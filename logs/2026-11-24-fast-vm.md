# 2026-11-24 Bytecode fast path

## What was wrong

Every variable read and write hashed its name into `env.vars` (then `globalVars_`), and every
expression walked the AST. A loop iteration cost about 140 ns and an action call about 450 ns.

## What changed

- New `src/runtime/fast_vm.cpp`: compiles an action, or a single `while` / `do` / `for` /
  `repeat` statement, to register bytecode with variables in numbered slots. Constants live in
  registers, comparisons fuse with branches, loops test their condition at the bottom, int
  arithmetic is inlined, frames come from a thread-local block stack.
- Subset: int/float/bool/string values, operators (with short-circuit), ternary, `if`, loops,
  `break`/`continue`/`return`, `print`, `let`/assignment (including declared-type checks),
  `x++`/`x--`/`x op= y`, string interpolation, calls to script actions, and `string.*`/`math.*`
  builtins with a plain registry return type. Anything else makes the compile fail and the
  tree-walker runs that code unchanged.
- Exactness: operations call the tree-walker's own helpers (`apply_binary`, `eval_binary_slow`,
  `to_display_string`, `eval_builtin_call`, `runtime_declared_type_matches`). Handles and
  struct-marker or handle-like strings never enter a compiled frame (checked on call and loop
  entry; otherwise the tree-walker runs). Callees that do not compile run through the
  tree-walker with the same binding. Loop state is written back to the env on exit and on errors.
  Disabled under the debugger, with dynamic actions loaded, or when closures captured locals.
- Entry points: `Runtime::fast_call` (both action call sites), `Runtime::fast_loop` (the four
  loop executors). Compiled code is cached per run and dropped by `ActionIndexGuard`.
- `exec_decl.cpp`: the declared-type inference lambda in `exec_let` is now
  `Runtime::runtime_value_type`, shared with the VM.
- Tests: `tests/semantics/fast_path.elan`, `fast_division_zero_neg.elan`,
  `fast_call_division_zero_neg.elan`.
- Docs: `docs/pages/examples/bench.md` (new numbers, what runs fast).

## Behavior changes

None intended. Only speed.

## Verification

Release build, best of 2, includes about 14 ms process startup:

| Script | Before | After | Speedup |
|--------|--------|-------|---------|
| 10M-iteration int loop | 1418 ms | 177 ms | 8.0x |
| `fib(27)` | 280 ms | 58 ms | 4.8x |
| 1M `string.len` calls in a loop | 472 ms | 200 ms | 2.4x |
| collatz to 300k + float loop + string build | 6460 ms | 848 ms | 7.6x |

- `cmake --build --preset release` and `--preset debug`: success, no warnings in `fast_vm.cpp`.
- `pwsh tests/run.ps1` on debug and on release: pass=94 fail=0.
- Discord plugin test and Docker plugin test (release): all pass. `python tools/check_builtin_registry.py`: exit 0.
- Every `.elan` under `tests/` and `examples/` (192 files) run with the previous release build
  and the new one, comparing exit code, stdout and stderr: only 4 differ, all time, random or
  UUID output (`tests/std/time.elan`, `examples/program.elan`, `examples/random/crypto_sha256.elan`,
  `examples/types/bench.elan` timings). `examples/random/server.elan` and
  `tests/std/process_json_math.elan` exceeded the 20 s timeout and were compared only through the suite.
- `compiler/main.elan` (self-host): output identical, no speedup (collection-heavy).

## Speed section in `examples/program.elan`

Added `speed()` with checked workloads (int loop 1e7, `fib(27)`, collatz to 1e5, float loop
1e6, 2e5 `string.len` calls on interpolated strings), called at the end of `main`. Compared with
the previous commit built in release mode outside the repository, best of 2:

| Section | Before | After |
|---------|--------|-------|
| int loop 1e7 | 1244 ms | 62 ms |
| `fib(27)` | 229 ms | 39 ms |
| collatz to 1e5 | 1642 ms | 210 ms |
| float loop 1e6 | 410 ms | 15 ms |
| strings 2e5 | 112 ms | 49 ms |
| total | 3637 ms | 388 ms |

The rest of the output, with UUIDs, sizes and times normalized, is identical between the two builds.
`erelang --check examples/program.elan`: exit 0.

## Not done

- Lists, maps, `for (x : list)`, method calls and indexing still run on the tree-walker. Values
  read from a collection can be heap, weak or file handles that the tree-walker releases at
  block exit; a compiled frame has to reproduce that before collections can move over.
- Builtins outside `string.*` / `math.*` (including `int()`, `len()`) are not compiled.
- Linux and macOS were not built here; CI covers them.
